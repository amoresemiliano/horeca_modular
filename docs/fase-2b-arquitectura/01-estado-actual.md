# 01 - Inspección y Análisis del Estado Actual (Fase 2B)

## 1. Metodología de Inspección No Invasiva

La evaluación del estado técnico actual de **Taquería El Criollo / Vegen Digital SL** se ha ejecutado mediante inspección estática de código fuente, archivos de configuración de dependencias y esquemas disponibles dentro de `el-criollo-ecosistema/`. No se han expuesto valores reales de variables de entorno, claves criptográficas, identificadores de cliente ni URLs privadas.

Para cada aspecto auditado se diferencian estrictamente los cinco niveles analíticos mandatados por la Metodología Vegen Digital: Hecho Verificado, Inferencia, Riesgo, Recomendación y Decisión Pendiente.

## 2. Hallazgos por Área Arquitectónica

### 2.1. Manifiestos de Dependencias y Construcción (`package.json`, `vite.config.js`)
* **HECHO VERIFICADO:** El manifiesto raíz (`el_criollo_modular/package.json`) declara un proyecto en React 19 (`^19.2.4`), compilado con Vite (`^8.0.1`) y estilizado con Tailwind CSS v4 (`^4.2.2`). En las dependencias de producción coexisten dos librerías de clientes de servicios en la nube: `@supabase/supabase-js` (`^2.100.0`) y `firebase` (`^12.11.0`). Para la lectura de archivos tubulares está presente únicamente `papaparse` (`^5.5.3`). No está instalada ni referenciada la librería `xlsx` ni homólogos para lectura de archivos Excel.
* **INFERENCIA:** El código del repositorio refleja una etapa de transición o exploración técnica en la que se evaluó integrar tanto el ecosistema Firebase de Google como la plataforma Supabase (PostgreSQL).
* **RIESGO:** El tamaño final del paquete compilado (*bundle*) se incrementa al importar en la interfaz de usuario dos SDKs completos con funcionalidades superpuestas. Asimismo, existe el riesgo de dispersión arquitectónica en el mantenimiento a mediano plazo si parte del sistema interactúa de forma heterogénea con distintos proveedores de backend.
* **RECOMENDACIÓN:** Definir con claridad la delimitación de responsabilidades de cada proveedor preseleccionado y diferir mediante carga dinámica (*lazy loading*) o funciones de servidor la ejecución de librerías especializadas en formatos complejos.
* **DECISIÓN PENDIENTE (D-20):** Aprobar en el momento de iniciar la Fase 2 productiva la estrategia de incorporación o encapsulamiento para lectura de formatos Excel transicionados desde el laboratorio.

### 2.2. Configuración de Nube y Variables del Entorno (`.env.local`, `firebaseConfig.js`, `lib/supabase.js`)
* **HECHO VERIFICADO:** En `.env.local` existen claves declaradas (cuantificadas mediante lectura estática de nombres, omitiendo valores): `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, y siete claves con el prefijo `VITE_FIREBASE_` (`API_KEY`, `AUTH_DOMAIN`, `PROJECT_ID`, `STORAGE_BUCKET`, `MESSAGING_SENDER_ID`, `APP_ID`, `MEASUREMENT_ID`). El archivo `src/firebaseConfig.js` inicializa el SDK de Firebase exclusivamente para el servicio de identidad y autenticación (`getAuth`). El archivo `src/lib/supabase.js` instancia el cliente de Supabase usando la URL y la clave anónima (`anon_key`).
* **INFERENCIA:** El sistema operado del lado cliente delega el control de sesiones en Firebase Auth, pero expone conexiones a bases de datos relacionales en Supabase haciendo uso del cliente REST inicializado con credenciales públicas del rol anónimo.
* **RIESGO:** Sin una configuración explícita de intercambio de identidad, las consultas al cliente de Supabase operan sin conocimiento del usuario autenticado de Firebase. Esto implica que las políticas RLS (Row Level Security) en el servidor relacional pueden resultar inoperantes, o bien requieren que las tablas se configuren con permisos de lectura y escritura para el rol anónimo, lo cual representa un riesgo considerable para la privacidad y confidencialidad del historial transaccional HORECA.
* **RECOMENDACIÓN:** Formular y probar un modelo de autenticación compatible que permita proyectar la identidad real del usuario al motor PostgreSQL, o bien interponer una capa de servicios o adaptador de identidad antes de pasar a producción masiva.
* **DECISIÓN PENDIENTE (D-21):** Seleccionar la estrategia definitiva de articulación de identidad (Migración nativa, Adaptador temporal o Intermediación por API/backend) analizada en el documento de autenticación.

### 2.3. Módulos Productivos e Implementación Actual de Extractos (`src/`)
* **HECHO VERIFICADO:** En el componente raíz `src/App.jsx`, el enrutamiento visual depende de `onAuthStateChanged(auth)` de Firebase Auth. Dentro del subdirectorio `src/modules/extractos/`, el archivo `ExtractosApp.jsx` efectúa peticiones de consulta directas sobre una única tabla plana llamada `extractos` en Supabase (`select('*')`), con un esquema de respaldo y lectura caché en el almacenamiento local del navegador (`localStorage.getItem('db_extractos')`). El componente `ImportModal.jsx` se apoya en `Papa.parse` para procesar exclusivamente cinco estructuras fijas de archivos CSV correspondientes a cuentas y tarjetas del Banco BBVA y Banco Sabadell.
* **INFERENCIA:** La implementación de `src/modules/extractos/` corresponde a una iteración inicial funcional pero acotada al ámbito del archivo CSV de dos entidades bancarias, incompatible de forma nativa con los ficheros Excel multicarta detectados en la Fase 1 y trabajados en la Fase 2A.
* **RIESGO:** El uso intenso de `localStorage` para respaldar históricos contables extensos de extractos (tales como las más de 36.000 filas acreditadas en el diagnóstico) corre el riesgo de superar las cotas de cuota de memoria del navegador (`QuotaExceededError`) y almacena de manera persistente registros económicos no cifrados en la máquina local del operador HORECA.
* **RECOMENDACIÓN:** Reemplazar el patrón de persistencia en `localStorage` por consultas paginadas desde la base de datos (`LIMIT` y `OFFSET`), gestionar el estado efímero en la memoria de trabajo de la SPA e impedir persistencias en disco del terminal local.
* **DECISIÓN PENDIENTE (D-22):** Autorización formal para desacoplar e integrar la lógica transicionada del laboratorio, jubilando progresivamente la interfaz monoválida del actual `ImportModal.jsx`.

### 2.4. Estructura y Cometido del Directorio `app/`
* **HECHO VERIFICADO:** El directorio `el_criollo_modular/app/` contiene un conjunto de archivos independientes constituido por HTML, CSS y JavaScript Vanilla (`app.js`, `index.html`, `menu.json`, `style.css`), desprovistos de frameworks de empaquetado o dependencias de Node. El código está orientado a presentar un menú digital interactivo apoyado en videos para clientes finales del restaurante, con hipervínculos para redireccionar hacia plataformas de reparto a domicilio según el local de origen.
* **INFERENCIA:** Se trata de una interfaz orientada exclusivamente al consumidor final (*customer-facing*), completamente independiente de la plataforma ERP y del Hub Económico operado en `src/`.
* **RIESGO:** El despliegue unificado sin delimitación clara de carpetas de servidor podría provocar confusión entre las rutas web públicas destinadas a la carta digital de comensales y el acceso restringido a la plataforma administrativa del restaurante.
* **RECOMENDACIÓN:** Mantener el aislamiento físico, lógico y de despliegue entre la aplicación pública de comensales (`app/`) y el sistema administrativo del ecosistema (`src/`).
* **DECISIÓN PENDIENTE:** Confirmar si en la configuración final de servidores el contenido del directorio `app/` se asignará a un nombre de dominio público o subdominio escindido respecto del portal ERP del restaurante.
