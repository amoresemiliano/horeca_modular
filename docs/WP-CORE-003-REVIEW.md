## Authorization and administration

Platform administration is resolved by `core_platform_can`, independently of organization membership. Only the active VEGEN_PLATFORM_ADMIN assignment plus the corresponding platform capability permits tenant lifecycle/entitlement administration and provisioning metadata. It grants no Finance reads or business RPC execution.

Organization administration uses authenticated, capability-checked, security-definer RPCs with fixed search paths. Tenant members cannot write identity/access tables directly, assign platform roles/capabilities, target foreign memberships or change their own access. Administrative changes serialize on the organization row. An active organization-wide OWNER must remain. Role, override, scope, membership state, tenant state and entitlement changes are audited without secrets. Effective permission inspection is server-evaluated and grouped by module in the UI.

There are still exactly 13 role templates. The eight new `banks.*` capabilities are granted by default only to OWNER. MANAGER is not broadened. Banks-only access profiles are application presets over CONSULTANT plus explicit capability GRANT/REVOKE overrides. Applying a preset replaces overrides atomically; it does not become a new authoritative role. Organization entitlements and user permissions remain distinct.

Navigation now requires an entitled module and a relevant effective capability; unknown roles no longer see all modules. Banks sections and actions have independent guards, reinforced by server gates and RLS. Transfer review, rule management and account editing no longer piggyback on classification/import permission. Generic classification and split retain `financial.allocation.edit`. Import upload/process/confirmation remain distinct capabilities.

Section access is checked by `core_banks_view`. All raw Finance reads require a Banks view capability and `sensitivedata.banking.read`. A user legitimately allowed to read Consolidado already possesses the raw amounts and can derive totals outside the application; section permissions govern application sections and their server gate, not the mathematical use of already-authorized data.

## Secure provisioning

`supabase/functions/tenant-user-invite` verifies the bearer token with Supabase Auth, creates an authorized invitation ticket, invokes Auth Admin invitation delivery, and completes the membership transaction through a service-only RPC. The final RPC rechecks the initiating authority and ticket age, rejects self-provisioning/identity mismatch, and does not overwrite existing memberships. Service keys and generated credentials are never returned to the browser. The invite/reset callback presents the password setup screen.

The initial role is explicitly chosen by the administrator. After invitation, the tenant admin can apply a Banks preset, capability overrides and operational-unit scope. Only tenant admins can alter an existing member's access; the platform console exposes member metadata and provisioning, not ongoing business access administration. Self-access changes require another authorized tenant administrator or the separate Master bootstrap process.

Auth email delivery and the database transaction cannot be atomic. A delivery or completion failure is reported honestly; pending requests remain auditable. An existing Auth user is not silently re-invited or reassigned. Delivery errors require administrator review. No password is generated by this UI.

References: [Supabase Auth Admin invitation](https://supabase.com/docs/reference/javascript/auth-admin-inviteuserbyemail), [server verification with getUser](https://supabase.com/docs/reference/javascript/auth-getuser).
