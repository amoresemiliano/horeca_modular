# WP-CORE-ROLE-001: baseline authorization review

Reviewed `dev` at `2038a1bf8606176d24f7a075e66c5a038bd93cd2`. This is a review of repository contracts, not a deployment or a verification of live configuration.

- Core already stores templates, capabilities and grants in `eco_role_templates`, `eco_capabilities` and `eco_role_template_capabilities`. Memberships enforce an `ORGANIZATION` role tier through a composite foreign key; platform assignments use a separate table. The existing administration RPC assigns only active organization roles and prevents self-modification and removal of the last active organization-wide OWNER. It does not implement role-template CRUD.
- The capability evaluator checks active membership and role, module entitlement, operational scope, and explicit revoke precedence. A new role-management contract must preserve those checks and must reject platform-scoped capabilities in organization templates. Deactivation of a role immediately removes effective access for its members, even though membership records remain.
- `core_admin_snapshot` currently authorizes tenant access through administrative write capabilities and returns users, grants, overrides, scopes and audit together. Merely allowing a new read capability to call this snapshot would expose more information than a narrowly scoped read contract; separate or filtered results are needed.
- Personnel's `personnel_admin_command` uses a single `personnel.employees.manage` gate for snapshot, schedule operations and employee administration. The snapshot combines employees, employment, schedules, punches, corrections, observations and devices. The UI also requires the broad manage capability. Granting it to Gerente would violate the requested restrictions. Granular capabilities need action-specific server checks, appropriately filtered reads, entitlement and unit-scope enforcement, and corresponding UI gates.
- Finance navigation requires the sensitive banking read capability in addition to the relevant section capability and enabled module. Existing read grants are `banks.consolidated.view`, `banks.summary.view`, `banks.metrics.view`, and `sensitivedata.banking.read`; a new role must not inherit the current MANAGER grants wholesale.
- Existing registry policies expose active role and capability records to authenticated users. Any new privileged snapshot must separately enforce its intended audience, and mutations must remain trusted RPCs with audit and reserved-role protections.

No role-management implementation, migration, live configuration change, or browser acceptance was performed as part of this review. The requested work remains open.
