# WP-FIN-005 contract review

The CSV and spreadsheet readers, batch preview, normalization, grouping and synthetic fixtures are client-side changes. Each confirmed file still uses the existing atomic import RPC. The proposed provenance extension is needed only to retain the additional minimized CSV and FX fields; the existing import function does not persist those extra fields.

The existing allocation update classifies one allocation and records `MANUAL`; the suggestion confirmation also records `MANUAL`. Neither can truthfully auto-confirm a pattern. Rule application records `RULE` but only produces suggestions, matches a substring and does not check two human examples and conflicts. Safe recognition therefore needs a server-side operation that checks the full semantic tuple and history under the same locks as classification and records automated results as `RULE`. Existing tables and provenance fields suffice; no new table or column is proposed.

The existing reconciliation RPC changes one allocation at a time and does not validate the target's tenant, product, amount, currency or date, establish reciprocal links, or set both economic types. Two calls can leave a partial pair. A server-side paired operation must validate both facts and update both atomically, using the existing reconciliation fields, and prevent later unilateral edits. It requires both Finance classification and reconciliation capabilities. The generic transfer workflow remains separate.

The proposed function requires authenticated Finance classification permission, checks tenant and current allocation versions, locks movement facts before reviewing, and rejects stale or invalid batches. PostgreSQL rolls back the whole call on error; retrying recognition leaves already confirmed allocations untouched. Group reviews are explicitly chunked and report partial completion if a later call fails. The current proposal locks all active organization movements and limits recognition to 2,000 rows per call; its scalability and deployment suitability require review before promotion. No shared database has been changed. Rollback requires restoring the prior function definitions and dropping the added functions, subject to review of any already-created reciprocal settlement links.

Existing `rpc_update_bank_allocation`, `rpc_confirm_finance_suggestions`, `rpc_apply_finance_rules`, and `rpc_finance_reconcile` were examined. The SQL proposal is a review artifact, not an approved or deployed migration. Its function-rewriting approach and paired-settlement lifecycle require further scrutiny and local integration and browser validation before release.
